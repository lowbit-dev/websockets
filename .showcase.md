The WebSocket protocol (RFC 6455) is fundamentally straightforward: a thin binary framing layer riding on top of a persistent TCP stream. Yet, if you look at the mainstream Go ecosystem, libraries treat this primitive like a full-blown application framework. They wrap sockets in asynchronous event loops, hide concurrency behind background goroutines, and impose opinionated messaging models.

When you force a network primitive into a heavy abstraction layer, you strip the calling application of its ability to manage scheduling, memory, and concurrency.

`lowbit.dev/websockets` was built as a corrective response. It is a synchronous, state-free protocol primitive that handles the complex framing, cryptographic masking, and compression math—leaving the execution topology entirely to you.

---

## The Trap: Hidden Magic and Heap Churn

The immediate consequence of high-level abstractions in network code is relentless heap churn. Standard implementations allocate separate memory blocks for every incoming frame header, construct scattered slices that trigger Go's escape analysis, and spin up hidden background goroutines to run automated keep-alive ticker loops.

When you add RFC 7692 (`permessage-deflate`) compression to the mix, the overhead escalates dramatically. A standard Go `flate.Writer` allocates hundreds of kilobytes of internal state dictionaries. If a server initializes a new compression engine for every single short-lived connection, the Go garbage collector quickly becomes overwhelmed by heap cleanup, resulting in unpredictable tail latency (P99 spikes).

Efficiency isn't an exercise in micro-optimization for internet-scale hyper-scalers; it is about predictability. It ensures your software runs cleanly, profiles legibly, and can saturate a multi-gigabit link on low-cost cloud infrastructure without breaking a sweat.

---

## The Solution: Explicit Lifecycles and Mechanical Sympathy

This package is designed around the reality of how the Go runtime and physical hardware interact. By removing the hidden state, we achieved multi-gigabyte throughput with zero hot-path allocations.

### 1. Allocation-Free Framing & Reusable Buffers

Instead of generating temporary slices that escape to the heap during frame parsing, frame assembly writes directly into a reusable, contiguous scratchpad tied to the connection's lifecycle.

By reusing an external byte slice in the application's read loop, the engine operates completely allocation-free on the network hot path.

```go
// Setup an acceptor with standard low-memory constraints
acceptor := websockets.NewAcceptor()

http.HandleFunc("/ws", func(w http.ResponseWriter, r *http.Request) {
    conn, err := acceptor.Accept(w, r)
    if err != nil { n
        return
	}
    // Explicit network and memory lifecycle management
    defer conn.Close()
    defer acceptor.Release(conn) 

    var buf []byte
    for {
        // buf slices directly into the pre-allocated scratchpad
        buf, op, err = conn.ReadMessage(buf[:0])
        if err != nil {
            break
        }

        // Echo payload back down the unmasked fast path with zero heap churn
        if err := conn.WriteMessage(op, buf); err != nil {
            break
        }
    }
})

```

### 2. Honest Allocation Boundaries

Hidden state fails silently. To prevent accidental memory degradation, the server-side `Acceptor` will strictly refuse to negotiate compression unless you explicitly configure it with a `DeflateConnPool`. This forces the developer to understand the memory footprint upfront, rather than finding out during a production traffic spike that an unpooled compression fallback is eating gigabytes of RAM.

On the client side, we maintain this honesty via explicit API options. If you want a single, long-lived client connection to pay a one-time initialization cost for compression, you must state it plainly at the call site:

```go
// Dial initiates a stateless connection using a standard http.Request
conn, err := websockets.Dial(req,
    websockets.WithMaxFrameSize(4096),
    websockets.WithUnPooledDeflate(5), // Explicitly named to highlight the allocation
)

```

### 3. Compiler-Optimized 64-Bit Masking

RFC 6455 dictates that all client-to-server frames must be processed using a 4-byte cryptographic XOR mask. A naive byte-by-byte loop hits a performance wall at roughly 1 GB/s because the CPU is processing data in tiny 8-bit increments.

Instead of introducing risky `unsafe` memory casting that breaks cross-architecture compatibility (such as Big-Endian systems), the engine utilizes Go's standard `binary.LittleEndian` package structured inside a bulk iteration loop. The Go compiler's SSA backend recognizes this pattern, strips away runtime bounds checks, and compiles the loop down into native, 64-bit CPU instructions. This optimization allows the client-side masked stream to run at an astonishing **2.6 GB/s**.

## Technical Highlight: Lookahead Streaming

Streaming large payloads through standard implementations often results in a wasteful, empty trailing frame (`FIN=true, Len=0`) just to signal to the remote peer that the message has concluded.

Both the raw and compressed streaming engines in this package implement a double-buffer lookahead strategy. By checking the finality of an incoming data stream *before* committing to a frame header, the engine naturally sets the `FIN` bit on the final block of data. Messages conclude cleanly on the wire with zero empty payload frames.

```go
func streamLargePayload(conn *websockets.Conn, largeFile io.Reader) error {
    // Segments and flushes an io.Reader in fixed 4KB fragments.
    // Memory consumption remains strictly locked to the chunk size.
    return conn.StreamMessage(websockets.OpCodeBinary, 4096 - 8, largeFile)
}

```

## What Was Omitted

To keep this package a true primitive, we deliberately chose not to build certain features:

* **No Internal Tickers:** There are no hidden background routines firing keep-alive frames. If your infrastructure requires pings, you explicitly invoke the blocking, context-aware `KeepAlive(ctx, interval)` loop inside a goroutine you control.
* **No Connection Maps:** There is no global registry tracking active connections. Grouping, broadcasting, and synchronization are purely application-level concerns.
* **No Handshake Parsing Bloat:** The package completely unloads the HTTP/1.1 handshake and connection hijacking mechanics by integrating directly with `lowbit.dev/cooper`.

By focusing exclusively on bare-metal transport efficiency, this package delivers a WebSocket layer that operates predictably, allocates nothing on the hot path, and steps out of your way.
